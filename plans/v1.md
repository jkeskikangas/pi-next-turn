# pi-next-turn v1: predict the next prompt, read ahead — Implementation plan

**Goal:** after each agent run, predict what the user will type next, show it in the TUI and on the phone (pi-mobile), and, when the prediction is confident, read the files that prompt will need before the user sends it. No Jev or other decision-model dependency. Nothing is written to the workspace ahead of time; edits ahead of time are v2 (`plans/v2.md`).
**Read first:** pi's `docs/extensions.md` (lifecycle: `agent_end`, `agent_settled`, `before_agent_start`; `ctx.modelRegistry.streamSimple()`; `ctx.ui.setWidget()`, `setEditorText()`; `pi.events`), `docs/sdk.md` (`createAgentSession`, `SessionManager.inMemory()`), `docs/session-format.md`; pi-mobile `src/protocol.ts`, `src/bridge.ts` (`agentSettled`, the `send` RPC), `web/app.js` composer; pi-jev-kit `src/seed.ts` (how a seed injects anchored files and emits `anchored-view`).
**Prior art:** Claude Code prompt suggestions (forked cached request, "2–12 words or nothing", 12 text filters, back-off; internals in picklog.cc, 2026-10-10), `@guwidoe/pi-prompt-suggester` (steering capture: accepted exact / edited / changed course), `pi-prompt-suggestions`, `@kliebhan/pi-prompt-autocomplete`. None runs work ahead of the user or measures prediction quality offline.

## Status (2026-10-12)

Implemented in this repo; the gates below decide defaults, not whether the code exists.

- **Step 0, measured** (`npm run spike`, openai-codex/gpt-6-luna): forked SDK session starts in 39–46 ms; its first request has the same prefix as the main session's next one (all non-message payload keys equal, 13/13 messages equal) and reads 95.5 % of its prompt from the cache. Two things were needed: the fork mirrors the tool declarations the transcript holds (`toolsAdded`, including `constrainedSampling`) in the same order, and replays the main run's system-prompt options in `before_agent_start`. `dispose()`/`abort()` stops a running fork within 11 ms. Live TUI in tmux: the widget renders below the editor (`› Fix it. · files ready  alt+n to use`), `alt+n` reaches pi and fills the editor, the injected files let the model edit without reading. `alt+enter` is pi's follow-up key, so the fill key is `alt+n` (D8).
- **Step 1, run twice, gate FAILED on the author's sessions:** round 1 (gpt-6-luna, 343 turns, 4 repos, k = 1/3/5, 2–12 words): top-candidate hit 0–2 %, coverage 0 % after calibration, no prediction at p ≥ 0.7, $0.003–0.017 per turn. Round 2 (gpt-6.1-sol, 200 turns, up to 30 words, k = 3/5): top hit 6–11 %, coverage 0 %, $0.28–0.46 per turn uncached. The author's next prompts are mostly long, new directions. **Similarity cut from labels:** the 100 pairs (`eval/out/pairs.json`) were labelled for same intent given the conversation (`eval/out/labels.json`, kept out of git because they hold session text). They were labelled by the implementing agent, not by hand, so the author should relabel them and rerun `--labels`. Result: 14 of 100 same intent; best cut 0.30 (F1 0.58); lexical similarity separates poorly (at 0.25: 9 true, 10 false positives). Round 3 (gpt-6-luna, 347 turns, 49 sessions, 7 repos, k = 3, cut 0.30): top hit 14 %, coverage 0 % after calibration, no prediction at p ≥ 0.7 → gate FAILED again; the calibration fitted with cut 0.30 is written to the author's agent dir. Per this step, the work stops here for a decision: the extension keeps the fitted calibration, which keeps it silent on such sessions (as designed: nothing below `pShow`). The package default `editedCut` stays 0.6 until labels from more than one user exist.
- **Steps 2–3, 5:** done (engine, TUI, events, pi-mobile on its `next-turn` branch). **Step 4:** done; its A/B measurement (`npm run ab`) needs turns where a prediction at p ≥ 0.7 matched; run over 84 of the author's recent turns (default calibration) it found none, so the gate cannot be measured on this data and read-ahead stays on but rarely triggers. **Step 6:** tooling done (`/next-turn stats`, `npm run refit` from live outcomes); the two weeks of use are pending.

- **Working ahead is opt-in** (decided after the gates): one setting `ahead: off | read | draft`, default `off`, replacing the `readAhead`/`draft` booleans (old config files are migrated). Step 4's gate was not passed, which per that step means read-ahead ships off by default; a one-time tip on the first shown prediction says how to turn it on.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **A standalone pi extension package, `pi-next-turn`.** pi-mobile and pi-multiedit integrate through `pi.events` only; neither depends on it, and it depends on neither. | Each package keeps working alone; the phone shows predictions only when the engine is installed. |
| D2 | **No decision model in v1.** Confidence comes from agreement between samples, calibrated on the replay eval (D5). A `Scorer` interface (`score(candidates, ctx) → {text, p}[]`) keeps a Jev scorer pluggable later. | Fewer dependencies; Jev must beat the baseline on the same eval to earn a place. |
| D3 | **Prediction = what the user would type, not a recommended step.** Claude Code's rules: 2–12 words, the user's style, no questions, no evaluations, no assistant voice, nothing when the next step is not obvious from the conversation. When the last assistant message offers options or asks a question, the candidates are those options. | The test is "I was just about to type that". |
| D4 | **Generated by a pi SDK agent session forked from the current one** (`createAgentSession` with `SessionManager.inMemory()` holding the active branch's entries, same model, same system prompt and tool definitions), prompted with one appended instruction. It reuses the main session's provider prompt cache, so the request is mostly cache reads. Tool use is refused in the instruction, every tool call is blocked through `tool_call`, and a reply containing one yields no prediction. The session is disposed after the reply. Triggered on `agent_settled` (final; nothing else will run). | One mechanism (the SDK session) for both prediction and read-ahead (D10); cache reads make it cost a fraction of a turn. |
| D5 | **An offline replay eval over the user's own pi sessions comes first** and gates every later step. Ground truth: the user message that actually followed. | Session files already pair context with the real next prompt; no labelling needed. |
| D6 | **Confidence = share of k samples whose top-1 candidates agree** (normalized text, token-set similarity above a cut set by the eval), mapped to a probability through a calibration table fitted on the eval's training split. k = 3 to start; the eval compares k ∈ {1 list of 5, 3, 5}. | A model's self-reported confidence is poorly calibrated; agreement is cheap with cached prefixes. |
| D7 | **Tiers by calibrated p:** below `P_SHOW` nothing; `P_SHOW` show; `P_READ` and above also read ahead (D9). Starting values `P_SHOW` = 0.35, `P_READ` = 0.7, replaced by the eval's expected-value cut: read ahead when p × (expected wall time saved) beats (1 − p) × (speculative cost converted at a configured rate). | Thresholds are guesses until measured. |
| D8 | **TUI: a widget below the editor, not a replaced editor.** `ctx.ui.setWidget("next-turn", …)` shows the top candidate (and up to 2 more when close in p). A shortcut fills the editor with it (`setEditorText`); a second shortcut cycles. Default keys `alt+enter` (fill) and `alt+]` (cycle), configurable. Shown only while the editor is empty; cleared on any keystroke that is not ours, on `agent_start`, and on session change. | Replacing the editor component conflicts with other editor extensions (`pi-prompt-suggestions` notes the same). Ghost text inside the editor can come later if pi gains an editor decoration API. |
| D9 | **Read-ahead = a speculative read-only agent whose output is files, not an answer.** It gets the conversation and the predicted prompt, the tools `read`, `grep`, `find`, `ls` only (a fixed allowlist; no bash), and the instruction to gather what the task needs and stop. When the user sends a prompt similar to the prediction, the gathered files go into that turn as already read, with `N#HH` anchors, the way pi-jev-kit's seed does, and each is announced with `pi.events.emit("anchored-view", {path, text})` so pi-multiedit counts it as read. Otherwise it is discarded. | Files help even when the user edits the prediction; the seed study measured −37…−52% turns from exactly this kind of context. Reusing a full speculative answer needs transcript grafting, which is v2. |
| D10 | **The speculative agent runs in-process with the SDK** (`createAgentSession` with `SessionManager.inMemory()`, same cwd, same model or a configured cheaper one), seeded with the active branch's entries (sharing the prompt cache as in D4), active tools restricted to the allowlist. Hard caps: 8 tool calls, 20 s, a token budget; aborted when the user sends anything or starts typing something unrelated. | Read-only on the same cwd needs no isolation; caps bound the cost of a miss. |
| D11 | **Outcomes are recorded for every shown prediction:** `accepted_exact`, `accepted_edited` (similarity above the cut), `changed_course`, `ignored` (the session ended or idled out). Captured in `before_agent_start` by comparing the sent prompt with what was shown. Stored with `pi.appendEntry()` (excluded from model context) and in an NDJSON log outside the workspace (`${PI_CODING_AGENT_DIR:-~/.pi/agent}/next-turn/log.ndjson`). | The live counterpart of the replay eval; feeds recalibration and the v2 gate. |
| D12 | **Back-off like Claude Code:** after 20 unused predictions in a row, show one turn in 10 until one is used. Skip when: fewer than 2 assistant messages in the session, the last run ended in an error or was aborted, a dialog is open, plan mode, `ctx.mode` is print or JSON. | Avoids nagging and wasted spend. |
| D13 | **Text filters are validated, not just written.** Start from Claude Code's 12 filters, minus the ones known to drop good prompts (`prefixed_label` drops `fix: …`; the unanchored `evaluative` match drops "greater"). Each filter must lower the false-show rate on the eval without dropping more than 1% of correct predictions. | Claude Code's regexes have measurable false drops. |
| D14 | **Events (the contract other packages use):** `next-turn:prediction` `{id, sessionId, candidates: [{text, p}], readAhead: "none" | "running" | "ready", at}`; `next-turn:clear` `{id}`; `next-turn:outcome` `{id, outcome, sent}`. | pi-mobile renders from these without knowing how predictions are made. |

## Steps

Each step ends with its acceptance check. A step that fails its gate stops the plan for a decision.

### 0. Spike: wire up and measure the decided mechanisms (half a day)

The mechanisms are decided (D4, D8, D10). The spike wires them up once and records the numbers later steps use.

1. A forked SDK session (D4) from inside an extension: start time, `cacheReadTokens` vs uncached tokens on Anthropic and OpenAI models (the eval's cost model uses these), and that `dispose()` aborts it cleanly mid-run.
2. The same session with active tools restricted to the read-only allowlist (D10).
3. `setWidget` below the editor plus `registerShortcut` gives a usable accept flow, and the chosen keys reach pi in Ghostty, iTerm2 and herdr/tmux.

**Done when** each has a measured answer written into this plan.

### 1. Replay eval (gates everything after it)

`eval/replay.ts` reads `~/.pi/agent/sessions/**/*.jsonl`, follows each session's active branch (parent links), and for every user message that has at least two assistant messages before it builds the context as it was, runs the predictor, and compares with the actual message. Sessions are split by session (not by turn) into calibration and test sets, 70/30. Default sample: 400 turns across at least 5 repos, newest first.

Measured per predictor variant (D6 k values, model choice, filters on/off):

- **hit rate**: actual prompt is `accepted_exact` or `accepted_edited` against the top candidate, and against any shown candidate;
- **coverage**: share of turns where something is shown;
- **calibration**: reliability bins and expected calibration error of p on the test set;
- **cost and latency** per prediction (tokens split into cache read, uncached, output);
- **read-ahead value** for turns above `P_READ`: precision and recall of files the speculative agent reads against files the real next run read (from its tool calls), and the share of the real run's read/grep/find calls that the read-ahead would have made unnecessary.

The similarity cut for "edited" is set by hand-labelling 100 pairs (same intent or not) and picking the cut with the best F1; the labels are kept in the eval directory.

Privacy: the eval sends past session content to the configured model provider, as the original sessions did. It runs only on explicit command and prints which sessions it reads.

**Done when** the report exists for at least two variants. **Gate to continue:** top-candidate hit rate ≥ 25% at coverage ≥ 40%, and at p ≥ 0.7 a hit rate ≥ 60% (calibration within 10 points). If the gate fails, try the variants once more (different k, model, prompt), then stop and report.

### 2. Prediction engine

`predict.ts`, `filters.ts`, `scorer.ts`, `gates.ts`, `similar.ts`, events (D14), `/next-turn` command (`status`, `on`, `off`, `stats`). Unit tests with a fake model client cover: gates, back-off, filter behaviour on the labelled pairs, calibration lookup, and that a reply containing a tool call yields no prediction.

**Done when** `npm test` and `npm run typecheck` pass and a live session emits `next-turn:prediction` within 3 s of `agent_settled` at the measured cache-read rate.

### 3. TUI

Widget, shortcuts, clearing rules (D8), outcome capture (D11). Tests: widget lifecycle on empty editor / typing / `agent_start` / session switch; outcome classification.

**Done when** a recorded live session shows the widget, fills the editor with the shortcut, and logs the right outcome for each of the four cases.

### 4. Read-ahead

`readahead.ts` and `inject.ts` (D9, D10). Starts when the top candidate's p ≥ the eval-derived cut. Aborts on send or unrelated typing. On a send similar to the prediction, injects collected files through `before_agent_start` (prompt sections, not a replaced system prompt) under the seed's size cap (40k chars) and emits `anchored-view` per file. A widget suffix shows `· files ready` when done.

**Done when**, on 10 replayed tasks where the real user sent the predicted prompt, the next run's tool calls and wall time are lower than without read-ahead, the same pass/fail as before (the same comparison method as pi-jev-kit's `docs/research/seed.md`), and an aborted read-ahead leaves no process or context behind. **Gate:** wall time on accepted turns −15% or better with unchanged outcome; otherwise ship v1 without read-ahead (flag off by default).

### 5. pi-mobile (in the pi-mobile repo)

- **Protocol:** add `{type: "suggestion"; id: string; candidates: {text: string; p: number}[]; readAhead: "none" | "running" | "ready"}` and `{type: "suggestion_clear"; id: string}` to the bridge's event union in `src/protocol.ts`.
- **Bridge:** subscribe to `next-turn:prediction` / `next-turn:clear` on `pi.events` and forward. No dependency on pi-next-turn: no events, no suggestions.
- **Web app:** up to three chips above the composer (`web/app.js`, per `docs/ui.md` and `docs/design-principles.md`); a tap sends through the existing `send` RPC, a long press puts the text in the composer to edit. In voice mode, the top candidate is read as "Next: …" and "yes" or "do that" sends it.
- **Push:** `agentSettled` already sends a "finished" attention after runs over 20 s. Wait up to 3 s for a prediction with p ≥ `P_READ` and add it to the notification body ("Next: …?"). A **Send** notification action (web push action; iOS category; Android action) is a separate step after the body change, because each platform needs its own handling.

**Done when** `npm test`, `npm run typecheck`, `npm run ui` and `npm run shots` pass in pi-mobile, and an end-to-end check (`test/e2e/`) shows chips appearing, sending, and clearing when the computer's user types first.

### 6. Live calibration and v1 release

Two weeks of the author's own use with logging on. Refit the calibration table from live outcomes, compare with the replay eval, and publish `/next-turn stats` (shown, accepted exact, accepted edited, changed course, cost).

**Done when** live hit rate is within 10 points of the replay eval's. **This is the v2 gate:** at p ≥ `P_READ`, at least 60% of predictions accepted (exact or edited), and read-ahead shipped on (step 4 gate passed).

## Risks

| Risk | Mitigation |
|---|---|
| An extension changes the system prompt per run, so a fork misses the cache | Step 0 records the cache-read share; `/next-turn stats` shows it live. |
| Predictions nag | Nothing below `P_SHOW`; back-off (D12); `/next-turn off`. |
| Read-ahead cost on misses | Only above the expected-value cut; hard caps (D10); live cost in `/next-turn stats`. |
| Injected files bloat context on edited prompts | Same size cap as the seed; inject only on a similar send. |
| Session content in logs | Logs live outside the workspace and record outcomes and lengths by default; full text only with `PI_NEXT_TURN_DEBUG=1`. |
| Key conflicts in terminals | Configurable keys; step 0 checks the common terminals. |
