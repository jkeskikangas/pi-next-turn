# pi-next-turn v2: draft the whole next turn ahead of time — Implementation plan

**Goal:** when a prediction is confident enough, run the predicted turn completely before the user sends it, edits included, without writing to the workspace. If the user sends that prompt (or a close variant), the prepared result appears at once and its edits are applied as one all-or-nothing commit. If not, everything is discarded.
**Starts only after** v1's gate (`plans/v1.md` step 6): at p ≥ `P_READ`, ≥ 60% of predictions accepted live, and read-ahead shipped.
**Read first:** `plans/v1.md` (D1–D14 hold unless replaced here); pi-multiedit `src/engine.ts` (`Planner`, `PlanFs`), `src/commit.ts` (`commit`, `ConflictError`, `drift`), `src/tool.ts` (`applyEdits`), `src/read.ts`, `src/shown.ts`; pi `docs/sdk.md` (`SessionManager` branches, `AgentSessionRuntime.fork()`); the speculative-execution literature: Speculative actions (arXiv 2510.04371), Proactive Thinking (arXiv 2607.03093), Speculate with Memory (arXiv 2607.12236).

## Status (2026-10-12)

Implemented ahead of the v1 gate (which failed on the author's sessions, see `plans/v1.md`), behind `draft: false` by default (`/next-turn drafts on`).

- **Step 0, hand-over calls found:** the `input` handler returns `handled` and schedules `pi.sendUserMessage("/next-turn-accept <id>")`; commands run before input handlers, so that runs with an `ExtensionCommandContext`. The command appends the prepared entries (actual sent text as the user message, system messages skipped) under the leaf through the session manager, resets the leaf, and calls `ctx.navigateTree(last)`, which refreshes the agent context and re-renders the TUI. The leaf may have moved since the fork only by entries outside model context (custom, label, session info). No new model run happens (integration test).
- **Live (tmux, gpt-6-luna, pi-multiedit `draft-mode`):** after "which line exactly?" the widget showed `› fix it now · draft: 1 file`; the speculation took 2.9 s, read 33.8k tokens from cache, cost $0.0005. `alt+n`, Enter: the prepared turn appeared at once (edit result, "Fixed math.ts:2"), the draft was applied (`return a + b`), and the `[pi-next-turn]` note listed the change. The drafted edit's result still reads "nothing written" above the note.
- **Tests against the real draft channel** (`test/multiedit.test.ts`): hand-over applies the draft; worktree checks pass on the materialized draft with the working tree untouched; a conflicting change under the drafted line writes nothing and the prompt runs normally.
- **E1:** one request/response channel `multiedit:draft` (`{op, …, reply}`) instead of separate event names, plus `multiedit:draft-ready`.
- **E6 partial runs:** a run stopped by a cap or a refused tool is never handed over; its draft is discarded.
- **E11:** `JevScorer` and `judgeSpeculation` implemented; opt-in (`scorer jev|auto`, `jevSafety`), no package dependency.
- **Step 3 eval run** (`eval/replay.ts --draft --draft-any-p`, real pi-multiedit drafts, nothing written, 10 replayed turns whose top prediction matched what was sent; none reached p ≥ 0.85, so any p was used): 1 of 10 speculations completed; 9 ended on a refused tool (these turns were operations: deleting branches, changing install sources), which is the intended stop. Drafted files matched the real run's edited files in 9 of 10, but trivially (both empty); file recall 0. Time to result −6 %. **Gate FAILED** (needs − 50 % and matching non-trivial drafts), so v2 stays behind `draft: false`.
- **Step 5 eval run** (`--scorer agreement,jev --jev-safety`, jev-latest through pi's model registry, same draws, 58-turn test split): Jev shows on 62 % of turns with top hit 17 % (agreement: 0 % shown, 14 %), but its p ≥ 0.7 predictions hit 36 % (ECE 0.31 vs 0.10): overconfident, so it **does not beat agreement** and stays opt-in. Safety check on 228 predictions: 2 judged safe, 0 of the 33 hits; no speculation at p ≥ 0.85 either way, so it saved nothing here and would have blocked every correct one. `jevSafety` stays off.

## What pi-multiedit already gives

`Planner` computes every edit in memory against an injectable `PlanFs` and produces `FileChange[] = {abs, before, after}`. `commit()` then refuses to write if any file on disk no longer equals `before`, writes atomically, and rolls back on failure. A draft is therefore a stored `FileChange[]` plus the edit requests that produced it; applying it is the existing `commit()`.

## Decisions

| # | Decision | Why |
|---|---|---|
| E1 | **Draft mode lives in pi-multiedit**, exposed to other extensions through `pi.events` (`multiedit:draft-open`, `multiedit:draft-apply`, `multiedit:draft-discard`, replies on `multiedit:draft-result`) and as exported functions for in-process callers. pi-multiedit never depends on pi-next-turn. | The edit engine owns edit semantics; drafts are useful beyond prediction (e.g. review-before-write). |
| E2 | **A draft is a scope:** `{id, cwd, changes: FileChange[], requests: EditRequest[], shown: Map}`. Inside a draft, `edit` plans against a **draft view** (`PlanFs.read` returns the draft's `after` for files already drafted, disk otherwise) and stores instead of committing; `read` reads through the same view. The result text says `drafted, not written` and otherwise matches a normal edit result. | Later edits in the same speculative run must see earlier ones, exactly like on disk. |
| E3 | **"What the model has seen" (`src/shown.ts`) is per scope.** Today it is one module-level `Map`; it becomes a map keyed by scope (the main session, each draft). | A speculative run's anchors must not validate bare line numbers in the main session, or the reverse. |
| E4 | **Apply = `commit(changes)`.** On `ConflictError` (the user or another session changed a file since drafting), replay the stored `requests` against the current disk through the existing re-plan path in `applyEdits`; anchors that no longer match make the apply fail with nothing written, and the result says which files moved. | Reuses the existing conflict-safe commit; a stale draft never overwrites newer work. |
| E5 | **Verification in a throwaway git worktree.** When the predicted task names checks (tests, typecheck) and the repo has a known command (from `AGENTS.md` or `package.json`), write the draft into `git worktree add --detach <tmp> HEAD` (with uncommitted changes copied first), run the command there with a time cap, and attach the result to the draft. The worktree is removed afterwards. | Bash cannot see an in-memory draft; a worktree isolates it from the user's files. |
| E6 | **Speculative full run.** For p ≥ `P_DRAFT` (eval-derived; starting 0.85), the speculative agent (v1 D10) gets the full tool set with: `edit` in draft mode, `read`/`grep`/`find`/`ls`, and bash limited to an allowlist of read-only commands (`git status/diff/log/show`, `rg`, `ls`, `cat`, and the repo's check commands run only through E5). Anything else ends the speculation at that point; the partial result is still usable. Caps: 40 tool calls, 120 s, a token budget. | Edits are safe in a draft; side effects outside the workspace (network, package installs, git writes) are not reversible, so they stay out. |
| E7 | **Handing the prepared turn over: a session branch.** The speculative run is a branch of the session (the predicted user message and the speculative run's entries under the current leaf). On a send that matches the prediction (`accepted_exact`, or `accepted_edited` above a stricter similarity cut set on the eval), the branch becomes the active leaf, its draft is applied (E4), and the prepared answer appears as the turn's result. On any other send, the branch stays as an abandoned alternative, the draft is discarded, and the files it read are injected as in v1 (D9). | The prepared turn becomes the real history with no extra model turn; a weaker match still gets v1's file context. |
| E8 | **Approval is the send.** Sending the predicted prompt is the same authorisation as sending it without prediction, after which the agent would have edited anyway. The prepared diff is shown in the TUI (and on the phone) as part of the turn. No draft is applied without a send. | Same trust model as the normal flow; nothing happens on accept-free paths. |
| E9 | **Concurrency.** One draft per session at a time. Drafts in different pi sessions on the same repo are independent; E4's conflict check resolves races. A new user keystroke that changes intent aborts the speculation and discards its draft. | Simple and safe; conflicts surface instead of being merged silently. |
| E10 | **Phone:** the `suggestion` event gains `draft: {files: number, insertions: number, deletions: number, checks?: "pass" | "fail" | "none"}`. The chip shows `· 3 files, tests pass`. The finished-push body includes the same summary; the Send action opens the app at the turn with the diff visible before it sends. | Writing to the working tree from a lock screen without seeing what changes is too blind. |
| E11 | **Jev is optional and comes last.** A `JevScorer` behind v1's `Scorer` interface (rank-then-verify over candidates) and a Jev safety check before speculation are added only if they beat the agreement scorer on the replay eval (hit rate at the same coverage, calibration error) and lower wasted speculation. | Same evidence bar as everything else. |

## Steps

### 0. Spike: branch hand-over

The mechanism is decided (E7); the spike works out the calls. Find how an extension: runs a branch in a background SDK session while the main session stays interactive; writes that branch's entries into the main session's tree; and makes it the active leaf when the user sends, instead of starting a new run for the sent prompt (likely in `input` or `before_agent_start`). Note whether the switch needs a command context (`ExtensionCommandContext`) and how the TUI re-renders the switched branch. Write the calls and any limits here.

### 1. pi-multiedit: draft scopes (in the pi-multiedit repo)

E1–E4: draft view `PlanFs`, draft-aware `read`, per-scope `shown`, store / apply / discard, replay on conflict. Tests (node test runner):

- edits in a draft leave the disk unchanged; a later edit in the same draft sees an earlier one; `read` in the draft shows drafted content with matching anchors;
- apply on an unchanged disk writes exactly the drafted bytes; apply after an unrelated change to another part of a drafted file re-plans and succeeds; apply after a change under a drafted anchor fails with nothing written;
- anchors seen in a draft do not validate bare line numbers in the main scope, and the reverse;
- the existing test suite passes unchanged (non-draft behaviour is untouched).

**Done when** `npm test` and `npm run typecheck` pass in pi-multiedit and the README documents draft mode.

### 2. Worktree verification

E5 in pi-next-turn (it decides when to verify); pi-multiedit provides `materialize(draftId, dir)`. Tests: uncommitted user changes are present in the worktree; the user's working tree is byte-identical before and after; the worktree is removed on success, failure and abort.

### 3. Speculative full run and hand-over

E6, E7 (with the calls found in step 0), E9. Extend the replay eval: for replayed turns where the real next prompt was predicted at p ≥ `P_DRAFT`, compare the drafted diff with what the real run changed (files, and whether the checks pass on both).

**Done when**, on 10 replayed accepted turns, time from send to finished result is −50% or better, with the same check outcome as the real run, and a discarded speculation leaves no files, worktrees or processes behind. **Gate:** if drafted diffs match the real outcome in fewer than half of accepted turns, keep v2 behind a flag and report.

### 4. TUI and phone

TUI widget suffix `· draft: 3 files, tests pass`; the prepared diff renders with pi-multiedit's diff renderer when the turn is handed over. Phone (E10) in pi-mobile: event field, chip summary, push body, Send action opening the turn. pi-mobile checks: `npm test`, `npm run typecheck`, `npm run ui`, `npm run shots`, e2e.

### 5. Optional Jev scorer (E11)

Run the replay eval with `JevScorer` and the Jev safety check against v1's agreement scorer and allowlist. Ship only if it wins on the eval's metrics.

## Risks

| Risk | Mitigation |
|---|---|
| A wrong prediction wastes a full turn of tokens | Only above `P_DRAFT`, set by expected value from live data; caps (E6); live cost in `/next-turn stats`. |
| A stale draft overwrites newer work | `commit()`'s `before` check plus replay on conflict (E4); failure writes nothing. |
| The speculative run has an irreversible side effect | Allowlisted tools only (E6); edits only in drafts; checks only in a worktree. |
| The user's working tree is disturbed by verification | Worktree outside the repo directory; byte-identity test (step 2). |
| Prepared answer no longer fits an edited prompt | Hand-over only above a strict similarity cut; below it the branch is abandoned and only its files are reused (E7). |
| Two sessions draft on the same files | One draft per session; conflicts surface at apply (E9). |
